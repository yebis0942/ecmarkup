そもそも:仕様書はどうビルドされている?

spec.html
tc39/ecma262 リポジトリの巨大な 1 ファイル
HTML + ecmarkdown 記法のハイブリッド
ecmarkup
TC39 公式ビルダー
→
ビルド成果物
index.html(単一ページ)
multipage/*.html(章ごと)
assets/ … ecmarkup.js + CSS
アルゴリズム手順などは markdown 風の ecmarkdown 記法 — 1. Let _len_ be ? LengthOfArrayLike(_O_). — で書かれ、ecmarkup がビルド中に tc39/ecmarkdown を呼んで HTML へ変換する
クライアント側は、素朴な vanilla JS
・フレームワークもバンドラも無し — js/*.js を連結して 1 本の ecmarkup.js に(メニュー・検索・ピン留め…)
・使うのは fetch と DOM API だけ
・ウィジェット追加 = js ファイルを 1 個足す+CSS を追記するだけ
手を出しやすい足場 — だから気軽にフォークできた

「ソース」が 1 つじゃない

Rails なら gem のソースを出せば終わり。
ECMAScript 仕様に「実装」は無い。
あるのはエンジンが4つ。
それぞれ組み込み関数の登録規約が全部違う →
V8
Builtin 名から復元/実装は Torque
SimpleInstallFunction(proto, "map", Builtin::kArrayMap)
JavaScriptCore
実装は ArrayPrototype.js
JSC_BUILTIN_FUNCTION…(mapPublicName(), arrayPrototypeMapCodeGenerator)
SpiderMonkey
実装が JS!
JS_SELF_HOSTED_FN("map", "ArrayMap", 1, 0)
QuickJS
map の実体は every + magic フラグ
JS_CFUNC_MAGIC_DEF("map", 1, js_array_every, special_map)
規約ベースで抽出 → 仕様の clause ID と突き合わせ = 493 セクション

「ES2021」はどのコミット?

素朴な答え:「リリースタグのコミットでしょ」→ ×
diff ツールは main 系列のスナップショットで動く。タグはリリースブランチの先にある。
解: git merge-base <tag> main
「リリースブランチが main から分岐した点」を各版の代表ハッシュにする。
例外:ES2016 のみ、スナップショットの収録範囲より古いため実リリースコミットをそのまま使用 —「歴史データには必ず例外が 1 個いる」

Q&A で聞かれそうなこと

Q. Annex B やコンストラクタ本体は?
A. v1 のスコープ外。対象はメソッド+アクセサのみ。
Q. リンク切れは起きない?
A. リリースタグ固定の permalink + CI がサンプル死活チェック。
Q. 本家 ecmarkup に提案しないの?
A. データが ecma262 固有で置き場所の議論が必要。まず自サイトで実績づくり。
